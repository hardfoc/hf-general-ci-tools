Documentation style guide

What every HardFOC documentation site contains, how its pages are written and what a README looks like. The pilot site, hardfoc/hf-tmc9660-driver, follows every rule here; copy its structure.

Voice

  • Plain and specific. “SPI mode 3, up to 10 MHz”, not “supports high-speed SPI”. Numbers, names, units.
  • Second person, present tense, active voice. “Call init() before anything else”, not “The init function should be called”.
  • Short sentences. One idea each. A paragraph is three to five sentences.
  • No hype, no filler. No “simply”, “just”, “easily”, “powerful”, “comprehensive”, “seamless”, “robust”.
  • No emoji in headings, lists or tables. No walls of bold. No exclamation marks.
  • Sentence case for titles and headings: “Bus settings”, not “Bus Settings”.
  • British or American spelling: either, consistently within a repository.
  • True statements only. Every API name, signature, pin, register and number is checked against the headers or the datasheet. When something is derived rather than measured, say so.
  • Never mention how the page was produced. No “generated by”, no tool or assistant names.

Every page

  1. A title (# Title, level one, exactly one), matching its navigation entry.
  2. A purpose line right under it: one sentence saying what the reader gets from the page. The theme renders it as the lead paragraph.
  3. Sections (##) in the order a reader needs them. A section that is only a link list belongs in a table or in the navigation instead.
  4. A next step when there is an obvious one (“Next: Porting”).

No Jekyll front matter, no Liquid. Material front matter is allowed only for hide: (the home page hides the navigation and table of contents).

Code

  • It compiles against the real API. In a C++ repository, every snippet longer than one line lives in tests/docs/*.cpp between // --8<-- [start:name] and // --8<-- [end:name] markers, is built by the host build (an OBJECT library, warnings on) and is included in the page with --8<-- "tests/docs/x.cpp:name". Instantiate the driver template over the documented port so the whole API is compiled.
  • It is the smallest complete thing. Includes, the object, the calls, the error check. No // ... in a block that claims to be complete.
  • It checks results. Every driver call returns a status: show what to do with it.
  • Names are real. A reader can paste them. One-line inline names (setTargetVelocityRpm()) are checked by searching the headers.
  • The README quickstart is a generated region (<!-- generated: quickstart-code -->) copied from the same compiled file, so it cannot drift.

Figures

  • figkit for architecture and anything drawn from the code: one module per figure in docs/diagrams/figures/<id>.py, data() reads the facts from the headers, build() lays out cards. The build refuses text under 4.5:1 contrast in either theme, overlaps and missing alt text; hardfoc-docs figures --check fails CI when the code changed and the figure did not. Embed with <!-- figure: id --> / <!-- /figure -->.
  • Mermaid for sequences and state machines.
  • Vendor diagrams only as SVG or compressed PNG, with { .hf-plate }, never screenshots of PDFs.
  • Alt text on every image: one sentence that says what the figure shows, not “diagram”. The build fails on a missing alt.
  • PDFs (datasheets, manuals) live in docs/datasheet/ and are linked, never embedded; the site links them on GitHub, which renders them.

Tables

Use a table whenever there are three or more items with the same attributes: pins, registers, parameters, options, commands, error codes, compile-time switches. Put units in the header (Range (V)), names in code font, and keep cells short; long prose goes under the table.

Links

  • Link pages by file ([Porting](porting.md#threads)); MkDocs checks them in strict mode.
  • Link repository files relatively ([inc/x.hpp](../inc/x.hpp)); the plugin turns them into GitHub links at the commit that was built.
  • Link the API reference with api/...html; the link check verifies it after Doxygen is merged.
  • External links go to the primary source (vendor page, datasheet, specification).

Core library (hf-core*, hf-utils-*, hf-*-interface-wrap, hf-pincfg)

Home (hero, what problem it solves, a feature list, a “used by” table), Quickstart (smallest use), Concepts (the model the library implements, with a figure), API guide (by task), API reference, Integration (CMake / ESP-IDF, configuration macros), Testing and CI, Changelog. A utilities collection gets one page per utility under Guides, each with purpose, a compiled example and complexity or memory notes.

HAL (hf-hal-*)

Home with a board card (hf-chip hf-chip--board): MCU, power, connectors, chips on board; Quickstart (flash an example, see output); Hardware (block diagram figure, pin map as a generated table from the pin configuration, connectors, power tree); Architecture (managers, how drivers are wired, figure); one guide page per board function; API reference; Examples; Bring-up and troubleshooting; Changelog.

Product (hf-* firmware products)

Home (what the product does, a photo or render with alt text, status), Getting started (flash, connect, first run), Architecture (tasks, data flow, figures), Operation (modes, commands, configuration), Hardware (link the HAL site), Development (build, test, release), Troubleshooting, Changelog. Decisions as ADRs under Reference.

CI and tool repositories (hf-general-ci-tools, hf-espidf-ci-tools, hf-espidf-project-tools)

Home (what it provides, a table of workflows or scripts), Quickstart (the smallest caller), one page per workflow or script (purpose, jobs and permissions, inputs table generated from the YAML, example caller, failure modes), Versioning, Migration guides, Changelog.

Organisation (.github, hardfoc.github.io)

The portal (hardfoc.github.io) is the org home: what HardFOC is, a card per product and HAL, a table of every driver with its chip, bus and docs link, and contribution links. .github holds the profile README following the README standard, plus community files.

README standard

The README is the front door on GitHub. It is short and points to the site.

  1. # Name and a hero line: one sentence, what it is and what it does.
  2. Badges that are true, in this order, only those that exist: CI (the main test workflow, branch=main), docs (the docs workflow, linking the site), license, latest release (only once a release exists). No coverage badge without coverage, no “PRs welcome”, no badge for a language version.
  3. The documentation link in bold.
  4. One diagram: the layer or block figure (figkit marker).
  5. A 30-second example: the generated quickstart region.
  6. What it does: five to seven bullets.
  7. Install: the submodule line and the CMake lines.
  8. Documentation: a table of the five or six most useful pages, linked to the site (/latest/...).
  9. Tests: one command line.
  10. License: one line.

No table of contents, no walls of emoji, no feature lists with check marks, no badges that link nowhere, no duplicated API tables (that is the site’s job).
